# コメント規約

## 目的

後続の読み手（Claude を含む）は渡された情報からしか判断できない。
コメントは crate・モジュール視点での役割と、他層（共通コア・データ契約・学習ワーカー・評価器・推論ランタイム・操作アダプター）との
文脈を埋め込み、ファイル単体で文脈が伝わる状態にする。

## 何を書くか

- このファイル・モジュール・関数の役割と責務境界（1〜2 行要約をドキュメンテーションコメントで）
- 呼び出し元・呼び出し先の文脈（「CLI の `evaluate` 工程から呼ばれる」「学習ワーカーを子プロセスで起動し JSON を受け取る」等）
- 他層との契約（定義ファイル・判定型・JSON 入出力・終了コード・配布パッケージ形式・前提条件・スレッド安全性）
- 評価契約に関わる不変条件（評価データの凍結・ハッシュ不変・推論関数へ渡してよい情報。[evaluation-contract](./evaluation-contract.md)）
- spec の対応（該当する場合は REQ-n・TASK-n を併記する。[spec-reference](./spec-reference.md)）
- 未実装・簡易実装箇所の将来仕様（スタブであることを明示し、目指す挙動と REQ-n を書く）
- 非自明な前提・副作用・エラー処理の意図（外部入力の検証根拠・資源上限の根拠・決定性 / 数値誤差の扱い・OS 差異の吸収理由）

## 何を書かないか

- コードを読めば分かる逐語説明（`i += 1;  // i をインクリメント` 等）
- 陳腐化しやすい実装詳細の重複（コードと 2 重に管理しない）
- spec 本文の長い引用（ID を示して spec を参照させる）

## ドキュメンテーションコメントの形式

- Rust: crate・モジュールの入口は `//!`、公開 API は `///` で 1〜2 行の役割要約を必ず付ける
- Python: モジュール・公開関数 / クラスに docstring（1 行目に役割要約）を付ける（[coding-python](./coding-python.md)）
- コメントは日本語で書く（[japanese-style](./japanese-style.md)）
- `unsafe` ブロックには `// SAFETY:` で理由と維持すべき不変条件を必ず明記する
