## 3. 学習の設定

- 追補 1 の 2 節と同じ設定にする（LoRA rank 8・scale 20.0・dropout 0.0、末尾 8 ブロックの全 Linear、Adam・定数 lr、batch 4、max_seq_length 512、損失・バッチの作り方・初期化・seed の扱い）
- 両モデルとも 28 ブロックのため、適用するのは第 20〜27 ブロックになる。学習可能パラメータ数は hidden_size で変わり、実際の数は `run.json` に記録する
- P15・P7 では `--dtype float32` を使わない（P7 は全体を float32 にすると約 30 GB で載らない）
- 格子は iters {300, 600} × lr {1e-4, 5e-5} の 4 構成とする。P15・P7 それぞれについて、seed 0 の validation 正解率が最大の構成を代表とする。同値は Macro-F1、さらに同値は iters が小さい方、さらに同値は lr が小さい方とする（adapter のサイズは格子内で同じなので使わない）。seed 1・2 は代表構成のまま学習する
- 選定には validation だけを使い、旧凍結 test と新しい評価データはどちらも使わない
- 採点の方法（追補 1 の 3 節。`<|im_end|>` を含めた条件付き対数尤度の合計、長さ正規化なし、8 件ずつの forward）は変えない

## 4. PoC ツールの資源上限の上書き

PoC 専用の引数で上書きする（#552）。既定値（0.5B 用）と製品のガード層（REQ-39）は変えない。追補 1 の 7 節（読み込み上限 1 GiB）は P だけに当てはまり、P15・P7 には下表を当てる。

| 上限 | 既定（P） | P15 | P7 |
| ---- | --------- | --- | -- |
| モデルファイルの合計バイト | 1 GiB | 4 GiB | 16 GiB（4 シャードの合計） |
| 読み込み時の同時保持・forward の見積もり | 8 GiB | 12 GiB | 24 GiB |
| 学習のメモリ（RSS と MLX ピークの大きい方） | 8 GiB | 12 GiB | 24 GiB |
| 学習の壁時計（`--max-wall-seconds`） | 3600 秒 | 7200 秒 | 21600 秒 |
| 採点の壁時計（`--max-score-seconds`） | 3600 秒 | 7200 秒 | 21600 秒 |

- 変更前後: 事前登録本文 4 節の「1 構成・1 seed あたり 1 時間」を、P15 は 2 時間、P7 は 6 時間に上書きする。理由はパラメータ数が大きいため
- 根拠: 実機は Apple M5・メモリ 32 GiB で、Metal の推奨ワーキングセット（`mx.device_info()` の `max_recommended_working_set_size`）は 24.96 GiB。P7 の 24 GiB はこれを下回る値とする。`sysctl iogpu.wired_limit_mb` は既定（0）のまま変えない
- P7 の学習ピークは約 21〜23 GB（max_seq_length 512 まで埋まる最悪値）、P15 は約 7〜8 GB と見積もる（推定）
- 壁時計は 0.5B の実績（600 iters で約 300 秒）からパラメータ数の比で見積もった（推定。P15 約 850 秒、P7 約 4200 秒）。予算到達の扱いは追補 1 と同じで、到達したらその時点の adapter で評価し、`budget_reached: true` を記録する
- P7 のシャードは `model.safetensors.index.json` に従って読む。index とシャードはすべて `SHA256SUMS` と照合する。index の受け渡しの形とサイズ上限は #552 で決める

## 5. 短時間試行と、載らない・学習できないときの規則

1. 代表構成を選ぶ前に、iters 10 の短時間試行を batch 4 で行う。最初の 1 step には、長さ順で最も長い batch を必ず含める（#552 で引数を足す）
2. 試行中は他のアプリを終了する。`sysctl vm.swapusage` の `used` をモデル読み込みの前と試行の直後に取り、開始時の load average、`mx.device_info()` の値、`mx.get_peak_memory()`、`max_rss_bytes` とあわせて記録する
3. 次のどちらかに当てはまったら「載らない」とする
   - MLX のピーク確保量、または RSS が 4 節の上限を超える
   - swap の `used` が読み込み前から 512 MiB を超えて増える
4. 載らないときは batch を 4→2→1 の順に下げて試行をやり直す。batch 以外の設定（iters・lr を含む）は変えない。batch を下げると学習に使うトークン数が減るが、iters を増やして補わない。この不利は結果に明記する
5. batch 1 でも載らなければ「載らず」と記録して打ち切る
6. 試行は P15・P7 の両方で行い、規則も同じとする
7. 本学習で P7 の代表構成、または seed 1・2 の学習が資源上限で止まった場合や、事前登録本文 8 節で不成立になった場合は、P7 を「不成立」と記録する。そのうえで、新しい評価データの採点より前に、主候補を P15 に差し替える。新しい評価データに P7 の予測を 1 件でも当てた後は、主候補を変えない。P15 も不成立なら判定不能とする
8. 量子化（QLoRA など）は別の候補になるため、今回は対象外とする

## 6. 評価の 2 段階

| 段階 | 評価データ | 扱い |
| ---- | ---------- | ---- |
| 参考値 | 旧凍結 test（`evaluation.jsonl`、sha256 `55b278edf015ad5707ddb050a9265f20555e50d5406a769f76940d8353928011`） | 判断には使わない。同じ評価データの使い回しのため甘めに出る。旧プロジェクト（`~/poc26/project`）の台帳で (P15, seed)・(P7, seed) ごとに 1 回だけ採点する |
| 正式 | 新しい評価データ（7 節） | 新 PoC 版の正式な比較とする |

- 作業の順序: 新しい評価データの生成・審査・凍結（#554・#555）を、P15・P7 の採点より前に終える（2026-10-14 決定）。凍結までは、どのモデルの予測も新しい評価データに当てない
- P15・P7 の採点は、`fandhe-edge-score` を P 系に対応させる改修（#553）の後に行う
- 参考値と正式は、同じ adapter（`run.json` の adapter の sha256）で採点し、両方の台帳に同じ sha256 が載ることを確認する。参考値を見た後に、学習・設定・主候補・判定規則を変えない
- 報告では正式の結果を先に置き、参考値には「同じ評価データの使い回しで甘めに出る」と必ず注記する
- 新しい評価データでは C1・C3 を 3 seed で学習し直す（`--compare` が同じ凍結 test の予測しか受けないため。#555）。P（0.5B）は既存の adapter をそのまま採点し、再学習も設定の選び直しもしない

## 7. 新しい評価データの作り方

| 項目 | 固定値 |
| ---- | ------ |
| 件数・ラベル配分 | 324 件。各 browser_* ラベル 12 件 × 25、none 24 件（capability 12・out_of_scope 12）。旧評価データと同じ |
| テンプレートと group | 各ラベル 6 テンプレート（none は capability 6・out_of_scope 6）、言い換え 2。1 テンプレートに 1 つの group_id（`ev2-<ラベル>-<2桁>`）を付ける |
| 作り方 | 旧評価データと同じ手順（`~/poc26/data/PROVENANCE.md`・`LABELING_GUIDE.md`）で生成する。テンプレートは train とも旧評価データとも別の内容の型から作る。行順は seed 0 の `random.shuffle` で並べ、並べた順に id（`ev2-00001`〜）を振る |
| 旧結果の遮断 | 生成の指示文は生成前に確定し、その sha256 を `PROVENANCE.md` と #554 に記録する。指示文と生成のセッションには、旧評価の候補別・ラベル別の結果（混同行列・誤判定の一覧・`evaluation_predictions.jsonl`）を含めない |
| 置き場所 | リポ外の `~/poc26/data2/`。来歴は同じ場所の `PROVENANCE.md` に書く。本文は issue・PR・ログに書かない |
| 文字の類似度（補助） | `input` を NFC 正規化して空白を除いた文字列の、文字 bigram の集合で Jaccard を計算する。各行について train の全行・旧評価データの全行との最大値が、どちらも 0.5 以下であること。超えた行は group 単位で差し替える。分布（中央値・最大・0.5 超の件数）を `PROVENANCE.md` に記録する |
| 型の近さ（主） | 生成者と別の審査者が全件をレビューする。審査者は審査中どのモデルの予測も見ない。近接重複の基準は旧データの第 2 回レビューと同じ（label を決める操作以外が値の差し替えだけ）で、train と旧評価データの両方に対して判定する。近接重複は 16 件（約 5%）以下とし、超えた分は group 単位で差し替える |
| 達成できないとき | 差し替えは 3 巡までとする。3 巡後も近接重複が 16 件を超える場合は、基準を緩めずに、残った件数とラベルを `PROVENANCE.md` と #554 に記録して凍結へ進み、結果に注記する |
| 審査 | ラベルの誤り（wrong）とツール名の漏れ（leak）は 0 件とする。曖昧（ambiguous）の指摘は直すか、group ごと差し替える |
| 必要件数 | 事前登録本文 5 節の仮定（b 側 0.15・c 側 0.05・検出力 0.8）で、Holm の最も厳しい段（α = 0.05/3）の必要件数は 215 件（`required_sample_size_mcnemar` による算出値。α = 0.05 では 168 件）。324 件はこれを上回る |

## 8. 有意性と判定

- 事前登録本文 5 節と同じく、seed ごとに McNemar の正確検定（両側）を行い、P 系の候補ごとに対 majority・C1・C3 の m=3 を 1 つの族として Holm 補正する
- 「C3 を有意に上回る」は、主候補について新しい評価データで、Holm 後 p < 0.05 かつ b > c が 3 seed すべてで成り立つこととする
- P 系同士（P・P15・P7）の比較は参考とし、判定には使わない

## 9. 省略する項目

- 容量・RSS・p95 の本測定（`measure.py`）は行わない。記録するのは、ファイルサイズ、学習時の `max_rss_bytes`、`predict` の時間統計だけとする
- 決定性の確認（事前登録本文 7 節）は P15 だけで行い（GPU で代表構成を seed 0 で再学習し、validation の予測の一致を確認する）、P7 では行わない。CPU での再学習による確認は行わない
- ONNX 書き出しは行わない
