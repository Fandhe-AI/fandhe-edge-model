# 推論の不一致発見時の原因特定・記録手順

対応: REQ-28（異常系）・TASK-28.2（#119）・M8・PoC-16。前提は TASK-28.1（#116・#117・#118）。
spec の内容は要約であり、詳細は spec の REQ-28・PoC-16（`03-poc/core-cli-vertical-slice/`）を参照する。

## 1. 目的と適用範囲

推論の結果が「一緒に処理するバッチの中身」で変わる不具合が見つかった場合に、原因の特定・修正・修正前後の不一致件数の記録を漏れなく行うための手順を定める（REQ-28 異常系）。

適用する場面は次のとおり。

- `crates/runtime/tests/full_match.rs`（単体・バッチ・評価器の 3 経路の予測ラベル全件一致。TASK-28.1-2・#118）が不一致を 1 件以上検出した
- 実前処理・ONNX 実装後（#112・#113）に同じハーネスを再実行して不一致が出た

## 2. 不変条件（緩めない）

詳細は [evaluation-contract](../../.claude/rules/evaluation-contract.md) を参照する。

- **凍結した評価データへの適用は 1 回だけ（REQ-27）**。原因の切り分け・診断には validation データかテストハーネスの合成データ（`full_match.rs` の 650 件等）を使い、凍結した最終 test は使わない。
  - 凍結した評価データに予測を当て直す必要がある場合は、それを「適用 1 回」として数えて回数を記録する。当て直すかどうかはオーナーまたは main が判断し、Agent は単独で実施しない。
  - 正解を読まずスコアだけを見る診断でも、評価データの入力に当てた事実と回数は記録する。
- **合格は不一致 0 件のときだけ**。浮動小数の許容差は 1e-9 のまま。スコア差の最大値は参考値として残すが合否には使わない。テストの skip・ignore、許容差の拡大、実機前提テストへの移動で不一致を消さない。
- **データ本文を記録しない**。記録してよいのは index・件数・ハッシュ・item id だけ。入力テキストを PR・Issue・ログ・本文書へ転記しない（security.md。`full_match.rs` の失敗出力も index と件数のみ）。
- **証拠の種別を明記する**（テストハーネス / 模擬 / 推定 / 実機）。仮説・推測・実測を区別して書く。

## 3. 検出

1. `label_mismatches`（`full_match.rs`）が返す不一致 index の一覧を取る。その件数が「修正前の不一致件数」になる。
2. その時点のモデル（重み・語彙）と評価データのハッシュ、コミット SHA、依存の版、実行環境を控える。

## 4. 切り分け（PoC-16 と同じ 3 段の順）

1. 前処理後の系列が一致するか（単体とバッチ、または Rust と Python でトークン列のハッシュを突き合わせる）
2. ラベルの対応（label_order）が一致するか
3. 予測ラベルが一致するか

1・2 が一致して 3 だけ不一致ならバッチ依存を疑う。1 か 2 が不一致なら前処理か定義の不具合であり、別の原因として記録する。

## 5. 原因の特定

- 同じ重み・同じ入力で、評価器側の予測をバッチ N とバッチ 1 で比べる。正解は読まず、スコアだけで診断する。
- バッチ 1 で不一致が 0 件になれば、バッチ内の他の入力（パディング長など）が結果に混ざっていると判断できる。
- 使うデータは validation データかテストハーネスの合成データにする（2 節）。

## 6. 修正と再実行

- 修正の例: 推論経路を 1 系列経路にそろえる（`crates/runtime/src/pipeline.rs`・#117）、評価器の予測をバッチ 1 にする薄いラッパーを使う。
- 修正後に同じハーネスで 3 経路の全件一致を再実行する。合格は不一致 0 件のときだけ。
- 凍結した評価データで再実行する場合は 2 節に従う。
- 判定に使わない参考測定でバッチ予測を使う場合の明記ルールは TASK-28.3（#120）で扱う。

## 7. 記録テンプレート

修正する PR の本文と対応 Issue に次の表を貼る。あわせて 9 節の記録簿へ 1 行追加する。

| 項目 | 内容 |
| ---- | ---- |
| 対象データ | 名前と件数（本文は書かない） |
| 修正前の不一致件数 | 件数と比率（例: 2/650） |
| 修正後の不一致件数 | 件数と比率 |
| 不一致の識別子 | index または item id（本文は書かない） |
| スコア差の最大値 | 修正前・修正後それぞれ。参考値で合否には使わない |
| 切り分けの 3 段の結果 | 前処理・ラベル対応・予測の各段の一致状況 |
| 原因 | 実測か推測かを区別して書く |
| 修正内容 | 差分の場所とコミット・PR |
| 変更しなかった処理 | 例: 推論・前処理・選定・採点 |
| 証拠の種別 | テストハーネス / 模擬 / 推定 / 実機 |
| 凍結評価データへの適用回数 | 診断での適用も含める |
| ハッシュ | 修正前後のモデルと評価データ |
| 実行環境 | 環境と依存の版 |

## 8. 実例: PoC-16

証拠種別: 実機（Mac）。spec（PoC-16・REQ-28）の要約。

- 修正前: 予測ラベルが 650 件中 2 件不一致。前処理 650/650 件とラベル対応 4/4 は一致。スコア差の最大値は 0.2135（参考値）。2 件とも 1 位と 2 位のスコア差が小さい接戦の事例だった。
- 原因の特定（診断）: 評価器側の MLX による予測をバッチ 128 で実行すると同じ 2 件が不一致になり、バッチ 1 では 0 件になった（スコア差の最大値は約 1.1e-6）。原因は、バッチ内で最長の系列に合わせたパディング位置の埋め込みが畳み込みの窓に混ざること。
- 修正: 評価工程の予測をバッチ 1 の薄いラッパーに差し替えた。推論・前処理・選定・採点の処理は変えていない。
- 修正後: 650 件中 0 件不一致。スコア差の最大値は約 9.4e-7（参考値）。
- 注記: この再実行は評価データへの 2 回目の予測適用になり、その事実を記録として残した。これは「修正後に最終 test を当て直してよい」という根拠にはならない（2 節）。
