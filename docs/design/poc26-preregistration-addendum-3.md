## 1. 日時・理由・結果の読み方

- 日時: 2026-10-19
- 理由: 2026-10-16 の判断（`poc26-result.md` の「判断の記録」）で、軽量化（4bit 化・共通プレフィックスの KV の使い回し）は採用の条件にせず、データとして測ると決めた。追補 2 の 9 節で省略した容量・p95・メモリを、ここで測る
- 読み方: 結果は記録のみとし、採否の条件にしない。KV の使い回しで計算量が約 1/18 になるという見積もりは推定（`poc26-result.md`）であり、実測で確かめる
- 証拠の種別: 以下は設計上の固定であり、測定値ではない。測定値は実機の証拠として記録する

## 2. 対象

- 対象モデル: Qwen2.5-1.5B-Instruct（P15）。revision は追補 2 の 2 節（`989aa7980e4cf806f80c7fef2b1adb7bc71aa306`）
- LoRA: 追補 2 で確定した代表構成 i300・lr1e-4 の seed 0・1・2 のアダプタを使う。新たに学習しない
- 対象外: 0.5B（P）・7B（P7）は測らない

## 3. 比較条件

| 台帳名 | 重み | 推論の方法 | 位置づけ |
| ------ | ---- | ---------- | -------- |
| P15 | bf16 | 追補 1 の採点（KV の使い回しなし） | 基準。既存の新 test 予測を使い、再実行しない |
| P15KV | bf16 | KV の使い回し（5 節） | 実装の正しさの確認（6 節）と、速度の比較 |
| P15Q4 | 4bit（4 節） | 追補 1 の採点 | 量子化の影響と容量の測定 |
| P15Q4KV | 4bit（4 節） | KV の使い回し（5 節） | 量子化と KV の使い回しを合わせた場合の測定 |

## 4. 4bit 化

- LoRA を統合してから量子化する。統合は W + scale·A·B で行い、scale は追補 1 の 2 節の 20.0 とする
- 量子化は MLX の `nn.quantize`（mlx==0.32.2。依存の追加なし）で、bits 4・group_size 64 とする
- 対象は Linear と埋め込みとする（mlx_lm の既定と同じ。埋め込みを共有する出力層も含む）
- 統合・量子化後に保存した safetensors のバイト数を容量として記録する（7 節）

## 5. KV の使い回し

- 1 件ごとに、全選択肢に共通な先頭トークン列（system プロンプト＋ユーザープロンプト）の K/V を 1 回だけ計算する
- 各選択肢の続きだけを、その K/V に続けて計算する
- 採点の定義は追補 1 の 3 節のまま変えない（選択肢ごとの対数確率・26 選択肢・8 件ずつのチャンク。`<|im_end|>` を含めた条件付き対数尤度の合計、長さ正規化なし）

## 6. 実装の正しさの確認

新しい評価データに当てる前に、次の 2 点を確認する。4bit は精度が変わること自体が測る対象なので、この確認の対象外とする。

| 確認 | 方法 | 合格条件 |
| ---- | ---- | -------- |
| (a) 合成モデルでの一致 | 合成の小さなモデルを float32 で動かし、KV あり・なしのスコアを比べる（テスト） | 全選択肢のスコア差が 1e-4 以内 |
| (b) 実重みでの一致 | P15 の seed 0 のアダプタで、validation 108 件について bf16（P15）と P15KV の予測ラベルを比べる | 不一致が 1 件以下。超えたら新 test の測定に進まず、原因を調べて記録する |

- (b) では、不一致件数と、選択肢ごとのスコア差の最大値を記録する
- (b) は validation だけを使う。新しい評価データと旧凍結 test は使わない

## 7. 測定項目

| 項目 | 方法 | 記録する値 |
| ---- | ---- | ---------- |
| 正解率 | 新しい評価データ（project2・324 件）で、(台帳名, seed) ごとに 1 回だけ採点する（`fandhe-edge-score`） | 正解率。P15 との McNemar の結果を参考値として出す。Holm 補正はせず、判定には使わない |
| 重み容量 | bf16 は `model.safetensors` とアダプタのバイト数の合計。4bit は 4 節の統合・量子化後に保存した safetensors のバイト数 | バイト数 |
| 1 件の時間 | `run.json` の scoring の mean・p95・max。warmup は 0 にして基準と揃える | 秒（mean・p95・max） |
| 推論時メモリ | 推論プロセスの最大 RSS と、MLX のピークメモリ（`mx.get_peak_memory()`） | バイト数 |

- 正解率の採点は、同じ adapter（`run.json` の adapter の sha256）で行う
- 正解率は結果の記録であり、P15KV・P15Q4・P15Q4KV の採否の判定に使わない

## 8. 測定環境

- 実機: Mac（Apple Silicon）。GPU を使い、他のアプリを閉じた状態で行う
- 条件は 1 回ずつ直列に実行する。条件どうしを並行しない
- 資源上限は追補 2 の 4 節の P15 の列と同じ値とする（モデルファイル合計 4 GiB・読み込みと forward の見積もり 12 GiB・学習のメモリ 12 GiB・採点の壁時計 7200 秒）
- 証拠の種別は実機とする

## 9. 失敗時の規則

- 採点（台帳の消費）は、予測ファイルが全 324 件そろってから行う
- predict が途中で失敗した場合は採点前なので、再実行してよい。理由を記録する
- 採点後のやり直しはしない

## 10. 結果の読み方

- 性能の目標（容量 40 MB・p95 250 ms・RSS 2 GiB）は目標扱いとし、超過は記録のみとする（2026-10-16 の合意。`poc26-result.md` の「判断の記録」）
- 測定結果は P15KV・P15Q4・P15Q4KV の比較として記録し、REQ-41 の扱いを変える判断の材料にはしない

## 11. 省略する項目

- CPU での測定
- 0.5B・7B の測定
- 量子化の別設定（3bit・8bit・group_size の違い）
- Rust 推論での測定
